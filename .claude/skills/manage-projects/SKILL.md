# Manage projects

Apply one change across every managed repo, verify each one with `doit preflight`, then commit when the user agrees.

## Context

- **Managed repos**: the first column of the "Managed projects" table in this repo's `README.md`. Each one is a sibling folder: `../<name>` relative to this repo (`/home/matt/gh/mm21/<name>`). Read the table every time; don't hardcode the list.
- **Tooling**: every repo uses [pyprojkit](../../../../pyprojkit/README.md) (sibling repo `../pyprojkit`; read its README and `src/pyprojkit/config` for the `ProjectConfig` / `ToolsConfig` API when you edit config).
  - `pyprojconf.py`: defines `config = ProjectConfig(...)`, the single source of truth
  - `pyproject.toml`: partly generated by `doit sync`. Never hand-edit fields marked `# pyprojkit-managed`; change `pyprojconf.py` instead. Hand-edit everything else (dependencies, `[tool.uv.sources]`, …)
  - `dodo.py` / `noxfile.py`: usually just the pyprojkit factories, though some repos add their own tasks (e.g. glyphsynth)
- **Environment**: each repo has its own uv-managed `.venv`, and `doit` isn't on the global PATH. Run everything as `uv run …` from inside the repo, e.g. `cd ../<name> && uv run doit preflight`.
- **pyprojkit pins**: repos pin it in `[dependency-groups].dev`, e.g. `"pyprojkit[all]>=0.8.1,<0.9.0"`. A bump to `X.Y.Z` becomes `>=X.Y.Z,<X.(Y+1).0`. Exceptions:
  - `pyprojkit` depends on itself (`"pyprojkit[all]"`, unpinned): skip the version bump there. Config changes still apply.
  - A repo with an unpinned `pyprojkit[all]`: say so and ask whether to add the pin, rather than deciding.
  - Make sure the target version exists on PyPI (`curl -s https://pypi.org/pypi/pyprojkit/json | jq -r '.releases | keys[]'`). If it doesn't (e.g. it's not released yet), stop and tell the user.

## Steps

### 1. Make the change

Interpret the prompt and apply it to every repo where it applies. Typical changes:

- **Bump pyprojkit**: first, once before touching any repo, run `uv cache clean pyprojkit`. uv's cached index often misses a release that was just published, and clearing the cache forces uv to fetch it again. Then in each repo, edit the pin in `pyproject.toml` and run `uv lock --upgrade-package pyprojkit && uv sync`. Don't run a bare `uv lock --upgrade`, which would upgrade unrelated dependencies.
- **Config change**: edit `pyprojconf.py`, adding imports as needed and matching the existing style (e.g. `dataclasses.replace(create_recommended_tools(), …)`). Respect per-repo differences: some repos pass extra `ProjectConfig` arguments or a customized `tools=`, so edit their config rather than overwriting it with a template.
- If an instruction doesn't fit a repo (e.g. the setting is already in place, or it conflicts with that repo's customization), skip that repo and say why.

If the prompt is ambiguous in a way that changes the edit (e.g. "set X" when X could go at `ProjectConfig` or tool level), check the pyprojkit source, then ask once for all repos instead of guessing.

### 2. Preflight

Run `uv run doit preflight` in each repo, which runs sync, init, format, analysis, test, badges and nox. Repos are independent, so run them in parallel with background Bash commands. Write each log to the scratchpad, since nox runs several interpreters and the output gets long.

Then look at `git status --porcelain` and `git diff --stat` and sort the changes:

- **Expected**: whatever you edited directly, plus `uv.lock`; `pyproject.toml` fields resynced from config; `badges/*.svg` (and badge cache-busting query strings in `README.md`); `.python-version`; `.claude/skills/pyprojkit-python/SKILL.md`; mkinit-generated `__init__.py` files when the change touched mkinit/doc config. Also the `build-system` fields with `uv_build_backend`.
- **Unexpected**: anything else, such as reformatted source files, changed `__init__.py` files that mkinit didn't need to touch, edits outside the files above, or managed fields the prompt didn't ask for. Show a short diff excerpt for each, and suggest a likely cause (e.g. a new formatter version from the bump).

Report one table, one row per repo:

| Repo | Preflight | Failed steps | Changed files | Unexpected |
| --- | --- | --- | --- | --- |

Below it, give a short note for each failure (the relevant error lines from the log) and each unexpected change. Don't fix failures or revert unexpected changes on your own: propose what to do and let the user decide.

### 3. Commit and push

Suggest one single-line conventional commit message for all repos, e.g. `chore: migrate to pyprojkit 0.9.0`, `chore: enable python_version_file`, `build: …`. Use `chore:` for tooling/config changes unless another type fits better, and say if any repo needs a different message (e.g. unexpected source changes the user keeps).

Then ask (via AskUserQuestion) whether to:

- commit the expected changes in each repo where preflight passed
- also push to `origin`
- include or exclude repos with failures or unexpected changes

Don't amend, force-push, or skip hooks. Afterwards, report each repo's commit hash and push result.
